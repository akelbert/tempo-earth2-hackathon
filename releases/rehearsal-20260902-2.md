- Helm release `jupyterhub`, revision 3, chart 4.4.1, deployed successfully in
  namespace `jupyterhub`.
- Hub, proxy, continuous image puller, and both user schedulers reached Ready
  with zero restarts.
- The GKE external Application Load Balancer uses the Terraform-managed reserved
  IP.
- The target HTTPS proxy has the out-of-band TLS certificate attached and its
  NEG backend is healthy.
- A direct hostname-to-IP HTTPS check returned HTTP 200 from `/hub/health` with
  successful certificate verification.
- The digest-pinned lab image ran as the non-root attendee identity on the
  NVIDIA L4 with driver 580.173.02, PyTorch 2.14.0, and CUDA 13.0.
- A CUDA matrix operation completed on the L4.
- FCN loaded from the baked 287.2 MiB cache without a model download.
- A real one-step FCN forecast ran on CUDA in 2.6 seconds with 1.02 GiB peak
  allocated GPU memory and produced `u10m` and `v10m`.
- The attendee Workload Identity read the six-scan TEMPO manifest and received
  a permission denial when attempting to write canonical data. No probe object
  was created.
- The disposable validation pod was deleted after it passed.
- Initial NativeAuthenticator signup attempts failed XSRF validation because
  Google used different `35.191.0.0/16` frontend addresses for the form GET and
  POST, while JupyterHub 5.5 included the apparent remote IP in its anonymous
  token identity. Helm revision 2 normalizes Google's frontend CIDRs through
  `JUPYTERHUB_XSRF_ANONYMOUS_IP_CIDRS`. Five independent external GET/POST
  cycles then returned HTTP 200 with XSRF accepted despite a different Google
  proxy address on every request pair.
- The rehearsal NativeAuthenticator administrator account was created
  successfully after the XSRF fix. The user accessed JupyterLab and executed
  `00_environment_check.ipynb`, which reported the NVIDIA L4 from the real
  single-user environment. Successful kernel execution also exercises the
  browser-to-kernel WebSocket path.
- The real administrator user pod ran on the L4 node with zero restarts, and its
  PVC was Bound to a dedicated 20 GiB event storage-class persistent disk.
- Helm revision 3 set `enable_signup: false`; the external `/hub/signup` route
  then returned HTTP 404 while the existing user pod remained Running.

The validation exposed a non-blocking Matplotlib warning: the released image's
`/tmp/matplotlib` configuration directory was created by root during the image
build. The Dockerfile now uses the attendee-owned persistent cache directory
`/home/jovyan/.cache/matplotlib`; this fix requires the next image rebuild.
